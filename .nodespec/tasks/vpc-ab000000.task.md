## Technology Guidance

_Reference for executing the Implementation Tasks above — apply where relevant. The task list stands even where this guidance is thin._

**Purpose:** AWS Virtual Private Cloud for isolated network boundaries. Use this as the technology for vpc roles when the deployment is on AWS. Provides CIDR-based IP address management, subnet segmentation, routing, and network access control.

**SDK Initialization:**
```
aws ec2 create-vpc --cidr-block 10.0.0.0/16 --tag-specifications "ResourceType=vpc,Tags=[{Key=Name,Value=my-vpc}]"
```

**Common API Patterns:**

#### Create Subnets
Create public and private subnets across availability zones
```
aws ec2 create-subnet --vpc-id vpc-xxx --cidr-block 10.0.1.0/24 --availability-zone us-east-1a --tag-specifications "ResourceType=subnet,Tags=[{Key=Name,Value=public-1a}]"
```

#### Security Group
Create security group with ingress rules
```
aws ec2 create-security-group --group-name web-sg --description "Web tier" --vpc-id vpc-xxx && aws ec2 authorize-security-group-ingress --group-id sg-xxx --protocol tcp --port 443 --cidr 0.0.0.0/0
```

#### NAT Gateway
Create NAT gateway for private subnet internet access
```
aws ec2 create-nat-gateway --subnet-id subnet-public --allocation-id eipalloc-xxx
```

#### VPC Peering
Establish VPC peering for cross-VPC communication
```
aws ec2 create-vpc-peering-connection --vpc-id vpc-requester --peer-vpc-id vpc-accepter --peer-region us-west-2
```

**Configuration Template:**
```
resource "aws_vpc" "main" {
  cidr_block = "10.0.0.0/16"
  enable_dns_support = true
  enable_dns_hostnames = true
}
resource "aws_subnet" "public" {
  count = 2
  vpc_id = aws_vpc.main.id
  cidr_block = cidrsubnet(aws_vpc.main.cidr_block, 8, count.index)
  map_public_ip_on_launch = true
  availability_zone = data.aws_availability_zones.available.names[count.index]
}
resource "aws_subnet" "private" {
  count = 2
  vpc_id = aws_vpc.main.id
  cidr_block = cidrsubnet(aws_vpc.main.cidr_block, 8, count.index + 10)
  availability_zone = data.aws_availability_zones.available.names[count.index]
}
```

**Best Practices:**
- Use /16 CIDR for VPCs to allow ample IP space; subdivide into /24 subnets
- Deploy subnets across at least 2 availability zones for high availability
- Separate public subnets (with IGW route) from private subnets (with NAT route)
- Use VPC Flow Logs for network traffic auditing and troubleshooting
- Plan CIDR ranges to avoid overlap when VPC peering or Transit Gateway is needed
- Use separate security groups per tier (web, app, data) with least-privilege rules

**Anti-Patterns to Avoid:**
- Using a single large subnet instead of segmenting by tier and AZ
- Opening all ports in security groups for debugging and forgetting to close them
- Overlapping CIDR ranges across VPCs that need to communicate
- Running NAT Gateway in a single AZ creating a single point of failure
- Ignoring VPC Flow Logs making security incidents harder to investigate

**Security:** Use security groups as stateful firewalls with deny-by-default posture. Add NACLs for subnet-level defense-in-depth. Never open 0.0.0.0/0 on SSH (22) or RDP (3389) in production. Enable VPC Flow Logs to CloudWatch or S3 for audit. Use VPC endpoints (PrivateLink) for AWS service access without traversing the internet. Restrict outbound traffic from private subnets to known destinations.

**Integration Patterns:**
- Internet Gateway for public subnet internet access
- NAT Gateway in public subnet for private subnet outbound access
- VPC Endpoints (Gateway for S3/DynamoDB, Interface for other AWS services)
- Transit Gateway for hub-and-spoke multi-VPC networking
- AWS PrivateLink for exposing services to other VPCs without peering
